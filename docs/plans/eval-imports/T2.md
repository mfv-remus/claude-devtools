# T2: Audit projectId / cwd coupling
Type: research (AFK) | Status: done | Blocked by: -

## Question
Where do main and renderer derive behaviour from `projectId` or from `cwd` inside session content, and what breaks or leaks for `import:<id>`?

## Needs answered
- Path-resolution entry points: `ProjectScanner.getSessionPath`, `SubagentLocator.getSubagentsPath`, `pathDecoder`.
- Content-derived fs reads to gate: `ClaudeMdReader`, `AgentConfigReader`, `GitIdentityResolver`, mentioned-file reads, anything calling `fs` with a path from a transcript.
- `validateProjectId` / `validateSessionId` rules and what must change.
- Renderer: places that decode `projectId` into a path, group by repo/worktree, or assume watcher updates.
- Services that must skip imports: FileWatcher, ErrorDetector, NotificationManager, SessionSearcher.

## Output
Table: file:line | behaviour | action (reuse / gate / skip). Appended to this file.

## Findings (read-only audit, local code; nothing run)

### 1. Path resolution: only a few places know where sessions live
| Where | Behaviour | Action |
|---|---|---|
| `main/utils/pathDecoder.ts:223` `buildSessionPath`, `:231` `buildSubagentsPath` | `path.join(basePath, extractBaseDir(projectId), ...)`. No check that the result stays under `basePath`; protection is only the ID validators | **Branch for `import:*`** (single place), and add an explicit "resolved path is inside IMPORTS_ROOT" check |
| `ProjectScanner.ts:969/976`, `SubagentLocator.ts:192` | thin wrappers over the builders, base = constructor `projectsDir` | reuse; they need access to the import resolver |
| `ipc/sessions.ts:226`, `SessionParser.ts:69` | call `getSessionPath` | reuse once builders are import-aware |
| `pathDecoder.ts:193` `extractBaseDir` | splits on last `~` (composite ids) | import ids must not contain `~` |

### 2. Validators (will reject `import:*` today)
- `ipc/guards.ts:47` `validateProjectId` -> `isValidProjectId` (`pathDecoder.ts:170`) -> `isValidEncodedPath` (must start with `-`, or legacy Windows form). `import:<id>` fails. Need a separate strict branch (fixed prefix + UUID regex), not a loosened general rule.
- `validateSessionId`: `^[a-zA-Z0-9][a-zA-Z0-9._-]{0,127}$` (`guards.ts:11`). Fine for UUID sessions. Eval traces need a mapped id (T4), never a path fragment.
- HTTP routes (`main/http/sessions.ts`) call the same validators, so one change covers IPC and HTTP.

### 3. Services that skip imports for free
`FileWatcher`, `ProjectScanner` listing and `SessionSearcher` are constructed with the fixed `projectsDir`/`todosDir`. If imports live in a separate `IMPORTS_ROOT`, they are never scanned, watched, or fed to `ErrorDetector`/`NotificationManager` (those hang off `fileWatcher` events, `standalone.ts:129-141`). So most "skip imports" rules from Q18 need no code, only a rule: **do not put imports under projectsDir**.

### 4. Content-derived file reads (important, corrects an assumption)
These are NOT triggered by the server decoding the transcript. The renderer takes `cwd`/`projectRoot` from session data and sends it to the server:
| Route | Server function | Renderer caller |
|---|---|---|
| `POST /api/read-claude-md` | `readAllClaudeMdFiles(projectRoot)` | `sessionDetailSlice.ts:356` |
| `POST /api/read-directory-claude-md` | `readDirectoryClaudeMd(dirPath)` | `sessionDetailSlice.ts:390` |
| `POST /api/read-agent-configs` | `readAgentConfigs(projectRoot)` | `sessionDetailSlice.ts:263` |
| `POST /api/read-mentioned-file` | `validateFilePath(...)` then read | `sessionDetailSlice.ts:482` |
- `http/utility.ts`: only `read-mentioned-file` goes through `validateFilePath` (sensitive patterns + allowed dirs). The other three pass the client path straight to the readers. (`ipc/utility.ts` NOT read in full; unverified.)
- What they return: CLAUDE.md readers return path/exists/charCount/estimatedTokens (sizes, not content). `readAgentConfigs` reads file contents (`AgentConfigReader.ts:56`); whether content is returned to the client is **unverified**.
- Consequence: my earlier Q16 statement about leaking `~/.claude` content was overstated for CLAUDE.md (sizes only). The gate still matters (wrong numbers, probing of paths in the container, agent configs), but the **gate must be in the renderer** (`sessionDetailSlice`: do not call these four for `import:*`). A server-side gate is impossible by path alone. Optional separate hardening: validate the three unvalidated routes against allowed roots (pre-existing, out of scope; raise with user).

### 5. Renderer
- `renderer/store/index.ts:73` slices `projectId` at `~`.
- `renderer/utils/urlRouting.ts:31` parses `/<projectId>/<sessionId>` with `decodeURIComponent`; the exact regex was NOT inspected (does it accept `:`?). Covered by T4.
- Grep found no renderer use of `decodePath`/`extractProjectName`; project display names are likely server-provided. Unverified beyond grep.

### Not verified
`ipc/utility.ts` validation, `urlRouting.ts` regex, full repo/worktree grouping in renderer, whether `AgentConfig` returns content.

### Impact on plan
- S3 shrinks: builders branch + validator branch + renderer gate in `sessionDetailSlice`. 
- Add to T4: URL regex and ID format. 
- New candidate ticket T8 (optional): harden unvalidated read routes (pre-existing issue, needs user decision).
